# 0004 How the munge key reaches compute nodes

**Status:** accepted, 2026-10-15

## Context

Slurm authenticates every message with munge. All nodes must share one
key, and anyone holding it can impersonate the controller. The common shortcuts
each leak it somewhere:

- A key generated by Terraform (`random_bytes`) lands in Terraform state.
- A key in user data is readable through `DescribeInstanceAttribute` and by
  any process on the node through IMDS.
- A key in git is public.

## Decision

1. The head node generates the key at boot from `/dev/urandom`.
2. It writes the key to SSM Parameter Store as a SecureString named
   `/<cluster>/munge-key/<head instance id>`. The head's instance role may
   put, delete and list parameters under `/<cluster>/` and nothing else.
3. Each compute node's user data names the parameter. Terraform knows the
   head's instance ID, so it can. The compute role may only `GetParameter`
   under `/<cluster>/`. Nodes poll until the key appears.
4. The head deletes keys left by earlier clusters at boot. Naming by
   instance ID means a new node can never pick up a stale key.
5. The boot scripts turn off shell tracing around the key and the
   slurmdbd database password, and the boot log is root-only. The database
   password is generated on the head and never leaves it.

## Consequences

- The key exists only on the nodes and in SSM, encrypted with the account's
  `aws/ssm` KMS key.
- The last cluster's key can outlive it in SSM until the next head node
  boots and deletes it. Standard parameters cost nothing.
